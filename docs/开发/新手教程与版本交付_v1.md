## 二、五课与步骤

每课使用1名教学玩家与19名预设玩家，报价样本固定，并通过独立教学种子调用**正式结算引擎**。这些预设报价不是正式AI的策略，也不替代20人格研究。各课彼此独立，上一课收益不转入下一课。

| 课程 | 实际操作与要点 |
| --- | --- |
| 第一次竞拍 | 选择A／B，修改整数报价；提交后观察共同基准线，再看高价与合作资格。合作不是独立行动按钮 |
| 四种报价数值 | 持有Steam大促和完美视力；25名义报价对应18实际扣款、31.25市场等价、25原始计分等价 |
| 扰乱与占位 | 每笔受资金50%上限约束；20扰乱对应50市场等价与25计分等价，实际占位但未持有赎回道具时不获奖 |
| 双行动与构筑 | 雅阁和以扫双竞拍；总额上限60，贡献两份市场样本、双行动修正×1；更多选择的毁奖仍按正式引擎呈现 |
| 观望与换层 | 预设仅剩20资金、已有123.456积分、屏障已消耗；观望不扣款、不加本房分，之后演示资金500、临时屏障重置、持久屏障不补回 |

常规步骤为 **选择／报价 → 共同市场 → 奖励资格 → 积分／资金 → 下一课**。最后一课再演示换层。

- 提交前只显示自己的四种报价数值，不显示其他玩家报价、基准线、资格或积分结果。
- 提交之后锁定本次教学输入，逐步展开已计算结果；可往回查看，不能通过“上一步”偷偷修改已提交报价。
- 重做本课才重新开放输入，相同样本、种子和报价得到相同结果。
- 可以跳课，完成页按实际练习过的课数显示，不把直接跳到最后一课记成五课全部完成。
- 双竞拍超预算时展示原合法性错误并禁用提交，不裁掉其中一笔后假装提交成功。
- 全场教学报价在提交后的折叠表格中可查，便于理解基准线为什么变化。

教程不伪造积分预测，不调整难度参数，不接入正式AI决策或人格随机抽取。

## 三、可见版本与更新记录

打开 **设置 → 版本与更新**：

1. 游戏版本，如0.2.0；
2. 当前真实构建：离线HTML读取自身元数据，普通网页读取源码指纹；
3. 规则兼容标识，独立于界面版本；
4. 新导出存档／回放v3，兼容读取v2；玩家档案仍为独立v1格式，不读取v1对局文件；
5. 更新内容与兼容说明，当前版本默认展开；
6. 可复制的版本反馈文本；剪贴板不可用时仍可选中文字手动复制。

界面版本提高不等于规则升级。0.2.7保持原引擎兼容标识，但按用户决定取消v1对局文件读取；已有v2中的历史构建身份保留，不伪造为当前构建。

版本维护位置：

- `web/package.json` 与 `web/package-lock.json`：应用版本；
- `web/release-notes.json`：按新到旧记录的更新说明，首项必须匹配应用版本；
- `web/release-config.json`：引擎与文件格式版本；
- `web/lib/ui/game-version.ts`：实际规则兼容指纹及页面反馈信息。

变更结算、经济、AI或随机流时需更新引擎兼容版本，并明确迁移策略；不能仅提高界面版本就把不同规则的旧局静默载入。0.2.6建立v2轻量检查点／差分回放，0.2.7移除v1读取；玩家档案独立版本不变，见 [存档v3](../归档/0.2/构筑与存档_v3.md)。

## 四、日常验收构建

```powershell
Set-Location -LiteralPath 'D:\The Bidding of Isaac\web'
npm run build:offline
```

输出仍保留 **`web/dist-offline/以撒的竞合.html`** 固定入口，方便在原文件地址刷新验收。同时生成：

```text
web/dist-offline/
  以撒的竞合.html
  以撒的竞合-0.2.0-{12位构建标识}.html
  build-manifest.json
  SHA256SUMS.txt
  更新与使用说明.md
```

两份HTML内容完全相同。分发时使用带版本与构建标识的文件，避免把不同代码都叫同一个文件名；HTML仍是独立单文件，不依赖旁边的说明或清单。

日常命令做类型检查与离线资源门禁，**不把未执行的全量测试记为发布通过**，清单中的完整发布验证为空。

固定验收入口不随版本改名，可减少当前浏览器地址变化。分发副本、更换文件名／位置或浏览器时，先导出对局JSON，再从新文件的设置页读取；浏览器自动存储不是跨文件地址迁移机制。

## 五、完整交付命令

```powershell
Set-Location -LiteralPath 'D:\The Bidding of Isaac\web'
npm run build:release
```

依次执行：

1. 检查版本、更新说明与当前文件协议是否一致；
2. 全量默认测试，记录通过与默认跳过数量；
3. 客户端、展示模型、构建脚本的定向lint；
4. TypeScript检查；
5. 普通网页构建；
6. 正式离线构建与单文件契约检查；
7. 更新固定验收入口，并写入带版本的交付目录。

任一门禁失败，不写入新的发布档案；已有版本不删除。测试、lint与类型检查日志保存在忽略的 `web/work/release-*.log` 中。Windows直接以Node启动本地工具，不用跨shell拼接文件操作。

交付目录：

```text
web/releases/v0.2.0/{12位构建标识}/
  以撒的竞合-0.2.0-{12位构建标识}.html
  manifest.json
  SHA256SUMS.txt
  更新与使用说明.md
  build-record-{UTC时间}.json
```

清单包含版本、构建ID、文件名、字节数、完整SHA256、兼容配置、更新记录、Git提交及工作区是否未提交、实际门禁结果。不会把有未提交代码的产物冒充为某个纯Git提交构建；取得不了Git状态时明确记为未知。

相同内容重建时保留每轮记录，最新清单可以反映之后已提交的源代码状态。若同一身份下已经存在不同HTML内容，会拒绝覆盖。版本文件和发布目录不进入Git，不清理旧交付，也不覆盖普通网页的文件来冒充离线产物。

这是本地交付管理，不创建Git标签、提交、PR或云发布；T11云托管仍后置。真实界面验收保持待用户反馈，不因自动门禁通过而标为已验收。
