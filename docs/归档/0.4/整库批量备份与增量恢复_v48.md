# 整库批量备份与增量恢复 v48

更新日期：2026-10-14；开发预览0.4.7。按用户要求先提交0.4.6为`c01050a`，未push；随后实现本批整库功能，本批不自行commit／push。

## 一、入口与备份范围

进度 → 对局记录 → 长期完整回放库 → **整库备份与恢复**。按钮位于逐份操作工具栏下方，经典／生存两页均可用；导出固定包含两个模式全部库资料，不受角色、难度或状态筛选影响。

- 原`index`记录：原物理键、首次保存时间、导出时间、原构建、来源、角色、难度、完成状态、大小与正文摘要，以及可保存的JSON扩展字段。
- 原`payload`记录：原正文字符串逐字保留，原本是无损压缩容器还是当前JSON均不改写、不重新压缩；保留可保存的JSON扩展字段。
- 原`removed`记录：旧原键标记、新可选`classicProof` v1及原删除时间均保留；不反推缺失说明。
- **不包含**localStorage续玩／最近回放、玩家档案／完成统计、界面偏好或游戏内存。已有各自备份入口继续独立。

导出不是只列索引，也不重新运行AI／随机数／登记完成局。缺失或孤立正文、坏索引／事实、未知证据版本、不可无损表示的非JSON字段等均整批失败，不生成悄悄丢数据的半份备份。

## 二、独立整库文件v1

格式`the-bidding-of-isaac-library-backup`，文件版本1、数据库版本1；包含导出时间／构建、三个完整记录数组和对规范化正文的SHA256摘要。仍使用.json；摘要用于完整性核验，不证明来源真实性。

| 边界 | 上限 |
| --- | --- |
| 回放数量／原已存正文UTF-8合计 | 100份／64 MiB |
| 每份回放与其解压后的当前JSON | 沿用8 MiB |
| 删除标记 | 8192条 |
| 索引、删除标记、正文行扩展元数据合计 | 16 MiB |
| 整库文件UTF-8合计（含JSON转义开销） | 160 MiB |
| JSON结构 | 深度32、100万节点 |

整库不是现有单局压缩容器1；不能为了整库方便放宽单份8 MiB，也不把64 MiB库额度当作单个对局文件限额。已存正文通常本身已压缩，不再整体重复gzip。达到备份边界时拒绝，不删除标记、不截断、不静默淘汰。标记增长与低内存大库仍需实测，边界不是通用浏览器剩余额度或磁盘占用。

## 三、预览增量恢复的冲突语义

文件先完整核验，再读取本机一致快照，逐份比较。预览显示新增、重复、本机删除保护、标记新增／已有／存活冲突和恢复后的数量／正文大小，支持逐份展开；勾选明确确认才可提交。

| 情况 | 本批行为 |
| --- | --- |
| 本机无该原键、也无本机等价或删除保护 | 新增原索引和正文，原来源／时间不改为本次恢复时间 |
| 本机已有相同原键或限定等价事实 | 保留本机首份原文、键、来源、时间，不覆盖 |
| 本机原键或限定说明凭据已删除 | 不复活，计入删除保护；逐份手动入库的原显式路径仍独立 |
| 备份标记在本机已有同键标记 | 保留本机原标记，不悄悄升级旧缺失说明 |
| 备份标记会影响本机仍存活的同键／等价记录 | 不删除记录，不覆盖为该标记；预览明确报告冲突 |
| 备份本身含不同原键的历史等价副本 | 空库原样恢复全部副本；比较只针对恢复前本机，不用新导入副本做相似链扩展 |
| 合计超过应用或备份边界 | 整批拒绝，不部分导入或清库腾位置 |

空库恢复的三个数组与导出时一致；非空库是明确预览的保守增量合并，不保证把本机变成源库的镜像，不提供清空、覆盖或批量删除。

## 四、一致性与失败保护

导出读取三个store的同一只读快照，逐份解压、语义／摘要核验后，再用只读事务检查原快照未变；变化最多重新读取三次，持续变化拒绝导出。

恢复预览是本实例的私有准备计划，不能凭伪造的计数对象写入。确认时在同一短readwrite事务比较全部索引、正文（包括额外字段／孤立变化）和删除标记，再只执行新增。没有事务内异步解压／摘要；失败或取消未完成事务时回滚全部store。

预览后发生自动归档、其他页面写入、正文替换或删除标记变化，则旧确认拒绝，要求重新核对、再次勾选；不偷偷重算已批准的新增集合。界面观察同页通知和focus，最终事务检查负责未通知的跨页变化。读取／导出／预览可取消；提交中禁用取消按钮，离开页面可中止尚未完成的事务，**已经完成的提交不会因为离开页面而撤销**。

原对局、草稿、玩家统计与最近回放不参与写入；恢复／导出不运行引擎，不新增完成统计。回放库数据库仍schema1；原v5对局、档案正文1、独立档案备份1、单份压缩容器1及正式游戏行为均不变。
