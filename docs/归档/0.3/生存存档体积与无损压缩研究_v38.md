# 生存存档体积与无损压缩研究 v38

> 2026-10-13，针对0.3.7存档便利性进行研究。只增加实验运行器和文档，不改变正式格式、存储键、游戏版本或HTML。压缩候选目前不能直接由正式导入器读取。

## 一、先区分三种文件

|文件|用途|正式七层样本A原始体积|
|---|---|---:|
|续玩检查点|恢复原阶段、草稿、AI策略和对局|86,291字节，约86KB|
|事实回放|独立查看全部已发生房间、评分、随机结果和最终榜，不跑AI|1,724,524字节，约1.72MB|
|完整备份|检查点＋事实回放＋玩家档案|1,811,225字节，约1.81MB|

所以“动辄1MB”主要是回放和完整备份，不是日常续玩检查点。现有HTML需要继续玩时可导出“生存续玩存档”；只有同时归档独立回放／玩家进度才需要完整备份。不同文件不是同一份JSON的三个名字。

数据使用v37两组真实正式曲线35房最高局（seed3，以撒／雅阁）及一组内部零线结构上限（seed42，雅阁困难）；结构样本不作为正式曲线平衡结论。备份中使用空玩家档案，已有大量历史或自定义扩展的玩家档案会增加实际体积。

## 二、为什么回放大

当前survival-facts-1是有界完整快照，不是经典v3那样的紧凑事实编码。35房的“房间”字段占约96%，规则快照仅约4KB，不是主要问题。

正式样本A：

|房间内字段|35房累计UTF8占用|占整个回放约比|
|---|---:|---:|
|结算后players|497,086|28.8%|
|入房playersBefore|475,715|27.6%|
|scoreBreakdowns|209,257|12.1%|
|events|138,365|8.0%|
|resolvedActions|84,245|4.9%|
|entryEvents|65,581|3.8%|

980份玩家前后快照中的库存数组约774,711字节，占整个回放约44.9%；库存实例出现10,471次，但只有324个不同实例ID。大量库存每房不变却被复制，实例ID、道具ID、获取序号等重复记录。库存属于players／playersBefore内部，上表与库存比例不能相加。

评分分解、行动四金额、原始／追溯／最终房分以及实际随机／特殊事件确实有价值，不能为减体积一概删掉。完整备份还同时携带可重建回放的检查点和独立事实回放，因此再次叠加约86KB；其读取目前先重建检查点，再核对嵌入回放一致性。

## 三、无损候选实测

Node v24.15.0，gzip级别6。JSON压缩封装是gzip二进制转Base64后的实验JSON，已计入约33%的Base64开销与实验头部。裸gzip更小，但正式UI需额外支持二进制读写；当前研究不假设浏览器已支持任何压缩API。

|样本／文件|原JSON|裸gzip|gzip＋Base64 JSON|引用去重JSON|引用去重＋gzip＋Base64|
|---|---:|---:|---:|---:|---:|
|正式A 检查点|86,291|13,877|18,592|98,193|22,657|
|正式A 回放|1,724,524|170,871|227,916|989,294|159,405|
|正式A 备份|1,811,225|约184,744|约246,416|1,005,468|约162,525|
|正式B 检查点|86,731|13,917|18,644|98,767|22,733|
|正式B 回放|1,755,335|173,503|231,428|999,669|161,085|
|正式B 备份|1,842,476|约187,378|约249,928|1,015,856|约163,537|
|结构C 检查点|82,087|13,254|17,760|95,843|22,109|
|结构C 回放|1,490,275|113,869|151,916|892,497|140,121|
|结构C 备份|1,572,772|约127,251|约169,756|912,622|约144,333|

备份日期与空档案生成时间会令gzip结果相差少量字节，故不把个位差异视作策略收益。上述是实验封装大小，不是已交付新格式的保证体积。

结论：

- 仅对现有JSON无损压缩就可使正式回放减少约87%，完整备份约86%，检查点约78%。
- 通用引用去重单独并不够：回放仍接近1MB，检查点反而增加。不能只凭“去重”二字认定更小。
- 引用去重再gzip可把正式回放进一步到约160KB，比直接gzip JSON再小约30%，但增加编码与别名／边界校验复杂度，不适合作为第一步全面替换。
- gzip不会减少解压后的事实规模或自动提高绘制帧率，完整一致性校验仍需执行。

## 四、另外两种轻量候选

### 检查点＋玩家档案，不嵌入独立回放

正式A实验约86,589字节，gzip JSON约18,812字节；B约87,029／18,864。已有引擎能严格重建全部房间事实，日常恢复可比完整备份轻很多。

代价是它不是永久独立回放归档：如果未来不再保留对应旧引擎，无法只读还原全部过程。当前client1就是回放可读、续玩不可读的例子。不能悄悄把“完整备份”改成不含独立事实回放，应该另外命名为轻量进度备份。

### 命令＋状态SHA256锚点，不保留大快照

实验保留种子、角色、规则上下文、策略、原始构建来源和全部命令，去掉完整snapshot，改为snapshot的规范SHA256：正式A/B约10KB，gzip JSON约2.5KB；结构C约12.6KB／2.6KB。样本中正式重建后的snapshot摘要一致。

这只是继续玩文件的另一种机制候选，不是现行v4可读取的格式。仍依赖保存的引擎与随机流版本，未知旧引擎不能重建；不能用于替代独立事实回放，也不能简单只存一个seed。摘要不是签名，文件安全边界仍须靠语义验证与数据保留。已经压缩的完整检查点约19KB足够轻，第一步没必要为再省十几KB改恢复内核。

## 五、实施优先级

1. **先做现有文件的无损压缩容器。**内层v4与摘要原封不动，解压后交回当前严格解析器。保留原JSON导入，明确识别新容器，读写不改变AI身份。默认小文件，原JSON可用于诊断。
2. **明确导出用途和大小。**日常“续玩”优先；“回放”“完整备份”清楚说明包含内容。是否恢复玩家进度仍需明确勾选，不因压缩而改变默认。
3. **浏览器验证。**测试离线环境、压缩能力或内置编解码方案、低性能设备、取消读取／迟到任务、损坏截断、解压后8MiB上限、深度／节点／实例上限；失败不覆盖原局。Node测量不等于浏览器支持或性能。
4. **再做生存专属紧凑事实编码。**借鉴经典v3的初始名册、库存实例表、前后差分、行动金额与事件引用，但必须适配动态活跃名单、淘汰冻结、层末S和种子同分。保留原始随机／评分权威事实，新增编码版本而非覆写survival-facts-1。
5. **长期回放库单独设计。**压缩虽能降低localStorage字符串占用，不能保证无限多局；需测真实配额，再考虑大事实独立存储及索引。

建议第一阶段交付目标：正式七层续玩约20KB、回放约230KB、完整备份约250KB（本批样本），不删数据，不迁移旧局。不是所有构筑和档案的硬上限。

## 六、研究验证与复现

研究模块在web/lib/ui/research/，客户端无引用，不生产正式候选文件。三组九份检查点／回放／备份，gzip解压和引用去重＋gzip解码后JSON逐字相同，原正式v4读取／重建验证通过；命令摘要候选与正式重建snapshot的SHA256一致。实验3项单元＋1项批量报告通过，类型与客户端lint通过，未将此前1076项说成新跑全量。

在本机，正式A/B回放gzip中位约15ms，解压约2ms，检查点gzip约0.9ms、解压约0.1ms；通用引用解码另约18～19ms，再执行原语义校验。均为Node预热后5次，不是浏览器测量。
