## 一、共同维护约定

### 1. 状态与确认

| 状态 | 含义 |
| --- | --- |
| 候选 | 名称、门槛、编号或展示仍在讨论；不计正式总数 |
| 暂缓 | 人类明确暂时不实施；保留条件与工程疑问，不计正式总数 |
| 已确认待实现 | 人类已明确确认该变更，尚未完成代码／验证 |
| 已实现 | 已进入运行代码，需单列自动化与实机状态，不能冒充已验收 |
| 已验收 | 有明确验收范围、版本与证据；某项通过不代表所有环境全部通过 |
| 已排除／弃用 | 保留排除原因或替代关系，不删除后重新占用旧ID |

其他模型的建议默认仍为候选；模型自行写“已确认”不是人类确认凭据。改表不等于改代码、自动发奖、push或实机验收授权。实机验收和push继续保持现有单独授权边界。

### 2. 如何修改

- 已实现区记录**当前代码现况**。提出新条件时先填“拟议变更”，不要直接覆盖当前行，让尚未实施的规则看起来已经上线。
- 修改顺序：新增变更编号→标出旧值／建议值／理由→人类确认→工程实现与测试→同步现行行和验证状态→保留变更记录。
- 稳定ID不可随意改号／复用；同一奖励不能因改名或合卡重新发一枚。新增候选ID明确标“暂定”，代码未注册前不代表编号已经保留。
- 后续讨论以本文为入口。原裁定和实施记录作为证据，累计阶梯首稿保留当时上下文，不再另维护一份“最新名单”。若发现表／代码／裁定不一致，先列出差异，不静默选一份覆盖其他资料。
- 给其他模型时，提供**本文＋这次想修改的ID或问题**即可。完整条件与例外在本文逐项详情，不要只转发短表丢掉判定边界。

### 3. 字段口径

- 分类A～F与徽章ID分开理解；等级铜银金、隐藏属性、适用模式彼此独立。
- “类型”是条件结构；“阶段”是正式记账事实。终局型不一定是名为final的事件，例如E06使用complete。
- “目标／单位”与完整条件一起阅读。C07的2是两种清零效果，E08的5是五种角色，不是两次／五局。
- “现行系列”记录显式子ID关联，S-HIGH／S-INTEREST／S-SURVIVAL为三级合卡；S-CLASSIC仅共享主题、仍是三张独立卡。没有关联的项为`—`，不能按颜色自动合卡。
- 首次版本指徽章加入的应用版本，不是等级配置版本。原30项为0.5.0；六项新增为0.5.3；札记从0.5.3加入，等级／隐藏配置从0.5.4加入，分段与新回显为0.5.5；24项新徽章及三级卡／新边界为0.5.6。
