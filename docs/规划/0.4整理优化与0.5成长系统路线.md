## 一、版本分工

**0.4：整理、优化与稳定性收口。**把现有经典／生存对局、保存恢复、回放库和进度入口整理成可靠、易用、可维护的一套体验。已完成的存储诊断与长期回放库保留，不重新建设，不在这一阶段扩展成长玩法。

**0.5：考虑成就与角色解锁系统。**先设计条件、进度、奖励和解锁规则，再实施；此为路线制定时范围。2026-10-15已按裁定接入第三批B自动记账，角色限制／UI尚待接入，见[当前实施计划](./0.5成就与角色解锁计划.md)。

本路线是对2026-10-13《0.3收口与0.4开发路线》的后续收敛，不改写旧阶段的版本、数据、验收和构建来源。

## 二、0.4范围与实施顺序

### P0：存档、恢复和实际环境验收

1. 固定现有0.4.0／0.4.1成果的提交基线；后续用户已要求commit并push，实际提交与远端状态见Git记录，未完成TODO不随提交标记完成。
2. 优先处理可复现的实玩故障：当前阶段、草稿、资金、道具、积分、淘汰、难度和AI续赛前后一致。保留原文件，每个确认问题增加防回归。
3. 补直接打开HTML、真实文件往返、其他浏览器和真实额度不足的验收。已通过的HTTP／模拟IDB测试不重复写成尚未实现，也不代替未完成的原生验收。
4. 跨模式切换、只读回放、导入预览／取消与返回保持原对局。库失败、档案失败与续玩失败分别提示，不静默覆盖或清理资料。

### P1：补齐现有数据管理，不扩展玩法

1. **独立玩家档案备份／恢复**：没有对局时也能使用；文件用途与校验独立，恢复前预览并确认；只处理档案，不替换两模式对局、草稿或完整回放库。首版不自动合并累计数据。
2. **基础进度统计与去重整理**：核对完成登记、重复恢复和跨运行时口径；若加入总局数／存活率等概要，累计与最近200条历史分开，不能反推已丢失历史。只读回放不计局，删除回放不减成绩。这里提供可靠的数据基础，不接成就目标、奖励或角色限制，不建设大型统计看板。
3. **整库批量备份／恢复与必要管理**：在逐份导出基础上减少重复操作；明确新增／重复／失败、容量和提交边界。库64 MiB应用上限与单份对局8 MiB限制不能混为一个容器限额。满库不自动淘汰，取消不清空旧库；批量整理按实际需要推进。

### P1：性能、界面与代码整理

1. 测保存／归档／读取／导出和35房回放交互，区分序列化、校验、摘要、压缩、事务与绘制；不把测试总耗时当作帧率或物理磁盘时间。
2. 优先复用同次终局快照和编码结果、减少重复大事实处理，再按测量决定调度或其他优化。IndexedDB库已经实现，剩余重点是原localStorage活动／最近回放路径的重复数据和开销。
3. 整理进度、榜单、回放、设置的布局、滚动、固定表头、焦点、提示与返回位置；修复现有体验，不为整理版本大规模重做页面。
4. 小步整理保存职责、公共文件处理、重复逻辑、说明与测试；每步有回归，不以重构名义改变权威事实、规则、最高AI、正式曲线或草稿语义。
5. AI、角色与教学保留实玩复验和确认问题修正，不把新一轮策略／赛制大改纳入0.4。紧凑编码仅在测量证明必要时再评估，不作为本阶段必须完成项。

**实际推进顺序：固定基线 → 可靠性修复与验收 → 独立档案 → 基础登记／统计整理 → 必要整库管理 → 按测量优化与界面／代码收口。**确认的数据故障随时优先；不为了追逐更多功能无限延长0.4。

## 三、0.4收口标准

- 现有两模式完整流程和保存／恢复闭环可靠，每个已确认阻断问题有复现、修复和回归。
- 数据管理职责清楚：续玩、完整回放、轻量历史、玩家档案和偏好不混用；失败与取消保留原资料。
- 主要性能问题有前后对照，原计分、随机结果与回放事实不变；桌面界面与返回交互完成复验。
- 当前说明、TODO、测试和构建来源一致，不重新引入旧v2/v3/v4读取工程。
- 功能收口与分发验收分开记录。直接file、原生下载、其他环境或发布门禁未完成时保持未验收状态，不用构建成功替代，不绕过既有工具限制。

完成这些后即可结束0.4整理阶段；成就与角色解锁不是其前置条件。
