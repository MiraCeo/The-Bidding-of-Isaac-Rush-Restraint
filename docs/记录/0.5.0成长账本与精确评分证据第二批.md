# 0.5.0成长账本与精确评分证据第二批

日期：2026-10-15。用户在[首批](./0.5.0成就规则层首批实施.md)后要求继续。应用仍0.5.0开发预览，本批实施P0-2后台基础及保存协调接口；尚未挂接正式对局生命周期、成就UI或选角限制，不提交／推送／发布。

## 一、E01证据：不改变旧v5状态结构

[item-scoring.ts](../../web/lib/game/item-scoring.ts)在原评分完成时，用原未舍入subtotal、同一已发生multiplier与同一四位roundTo计算未清零应得分；原score、triggers、随机调用与返回对象字段完全不变。结果通过WeakMap非枚举旁路保留，readLiveScoreBeforeClear读取同一评分对象的证据。

这是**进程内评分证据**，不是永久存储，也不是“新游玩”的授权：存档重建也可能运行评分，不能根据旁路存在就给旧事件发奖。真实正式结算的适配／记账必须在回放JSON复制之前读取，并在合格事件成长凭据中保存该四位值。当前快照、复制、旧原v5回放不会被伪造出新增字段；没有证据仍明确待补，不从舍入后分项倒推。

因此本批没有改v5字段白名单、事实编码、兼容身份或原780状态golden，不采用“统一删除新增字段后哈希”的放宽。精确证据只进入独立成长模块的紧凑事件数据。BOSS房新获心脏的追溯仍不进入此评分阶段证据；既有心脏倍率按原评分计算。

验证包含原始正数舍入为0、行动分项舍入全0但倍率后的正式分为正、观望零分、多种触发和额外随机调用为0。经典780状态原始完整hash仍按原断言核对，不重建期望值。

## 二、有版本的成长账本

| 源码 | 职责 |
| --- | --- |
| [event-codec.ts](../../web/lib/ui/achievements/event-codec.ts) | 四阶段分析事实的紧凑、严格可逆编码；正常竞拍结果、原因flags、机会／件数及精确分数分开 |
| [registry.ts](../../web/lib/ui/achievements/registry.ts) | achievementRegistryV1显式启用、严格校验、逐结算去重、分支前缀、成长与权限投影 |
| [persistence.ts](../../web/lib/ui/achievements/persistence.ts) | 注入式同源排他写入、单键完整候选提交、配额／坏资料／取消及重试边界 |
| [registry.test.ts](../../web/lib/ui/achievements/registry.test.ts) | 评分证据、编码、旧档案保留、重复／分支、协调、备份及容量验证 |

档案正文仍v1，新模块放progression.modules.achievementRegistryV1。格式固定version1／catalogVersion1、activatedAt、manualUnlockAllAt和receipts；每份凭据保存key、root、parent、authorityHash、mode、at、stage、position与紧凑values。

- root须由未来生命周期层根据核验后的对局身份及迁移排除基线建立；不能每次导入随机新建。
- authorityHash须标识完整权威事实，不是只根据成就计数／flags生成的摘要。当前接口只接受已经可信的后台输入，未提供新的用户文件领取通道。
- key按模式、root、parent、权威摘要、阶段和位置生成，重复完整单元返回原档案不写；同键却有不同成长证据拒绝。
- parent必须在同账本内更早存在、同root同模式、阶段／位置严格推进且不能接在终局后。不同真实分支复用相同已入账父前缀，旧前缀不重复累计，单局连续／清零状态从该分支父节点继承，而不是用生涯累计代替。
- 历史、只读、教学source不创建模块、不新增凭据；这仍需未来控制器正确提供来源，不能将一个布尔值／字段当完整迁移保障。
- 成就进度、达成时间、累计与单局状态从有界凭据确定性推导，避免另存一套容易矛盾的累计；同局达标后不因后续连续数清零撤销。
- 角色授权独立由manualUnlockAllAt或固定成就组合投影，一键授权不改成就事实或累计；已由成就开放的更早时间不被后来的手动点击覆盖。

## 三、旧档案与校验

readPlayerProfile增加对已存在成长模块的严格核验；**读取没有模块的0.4档案仍不自动初始化**。显式activate才创建空成长账本与默认以撒权限，旧历史、累计、statistics、旧预留achievements／characterUnlocks及其他扩展原样保留，不解释为0.5成就或权限。

这避免为迁移删旧字段。当前模块成为未来0.5界面的权威来源，旧预留字段不授予0.5权限；普通重读合法模块不再次迁移。坏／未知版本模块拒绝并保留原档案，不当作空模块重建。档案解析、原JSON／压缩备份自然包含并校验模块，不重放发奖。

独立玩家档案与本局经典完整备份仍沿用原格式。明确恢复更早0.5档案允许回退到快照；恢复0.4档案不会因读取自动发奖，后续显式启用再建立新空账本。普通读档不是用户明确替换，不可重新锁回合法授权。

## 四、保存协调与容量

persistAchievementProfile先取得bidding-profile-write:bidding-player-profile-v1同源排他协调，再在临界区重读原文，调用既有完整档案候选提交；更晚入场的写入基于最新档案，不覆盖排队期间的新资料。记录／计数／达成／权限作为同一模块一次写入；配额失败不留下半模块，重试只记一次。

可注入协调器用于确定性测试，浏览器适配使用Web Locks。缺少协调能力明确拒绝新成长写入，不默默降级成“全局锁”；等待期间signal取消在执行候选前再次核对，迟到回调不写入。已经成功提交的写入不承诺随页面离开撤销。

**目前仅新成长接口加入这个锁。**原完成统计、档案替换／本局恢复还没有改接同锁，不能宣称已解决所有跨页并发或崩溃事务。下一批必须统一相关写入参与与对局元数据恢复，控制器正式接入后才能宣称完整闭环。

成长凭据独立上限2048条、模块正文896KiB，继续受整个档案1MiB约束；原完成凭据8192与历史200条不变。任何上限先到即停止新增候选，保留旧事实／累计，不自动删除凭据或伪造成功。双行动同房仍是一个结算凭据；进房与房间各自独立。

容量测量用2048个合成独立根凭据，不冒充2048局游戏或带200历史／8192完成标记的最坏档案。真实父链、已有其他模块会更早受字节上限约束，不能以一个样例宣称所有最大组合都可容纳。测量值保存于web/work/v050-achievements-p0-2/capacity.json。
