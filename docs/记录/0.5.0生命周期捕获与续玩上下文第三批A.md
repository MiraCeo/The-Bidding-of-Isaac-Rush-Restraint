## 二、旧局基线不是简单房号

位置采用明确阶段顺序：每层进房／房间结果／层末／终局分别编码，excludedThrough是升级时已经发生的最大阶段边界。旧room_action已完成进房钱但报价未结算：旧进房排除，新报价可以捕获。旧room_result／排行排除该房已结算事件，只捕获后来新进房。

旧真人淘汰、仅AI后来产生终局时，没有新真人淘汰单元，因此不能借新终局授予F05；F04不能把旧前两层借给新第三层。只读导入／预览／解析不调用applyGrowthContext，无自动补发。

已知context不存在时不根据0.5导出日期猜旧事件已合格。新context恢复必须在隔离的既有检查点核验过程中重建全体单元，核对模式、match root、排除边界、位置、原因数据及完整前缀摘要；不是只有checksum正确就信任成长flags。

## 三、明确的v5可选扩展

本批保持对局文件头version5、用途及引擎兼容身份，**仅显式支持growth上下文1**：

| 用途 | 字段位置 |
| --- | --- |
| 经典检查点／本局完整备份 | 顶层growth，可缺省；还原为GameSession.growth |
| 生存检查点 | 顶层growth，可缺省；还原为SurvivalSaveDocument／ClientSession.growth |
| 生存完整备份 | 配套checkpoint中的growth；外层不额外放另一份 |
| 只读回放、独立档案、整库 | 不增加growth；各自原协议保持 |

0.5新读取器继续接受没有growth的旧v5，但不补历史；旧0.4读取器仍严格拒绝带新字段的文件，**不能宣称新带字段文件可交给旧HTML续玩**。保存／恢复只放宽这个具名且严格校验的扩展，其他未知字段、growth未知版本、模式冲突和原v2／v3／v4仍拒绝并保留原资料。

单位最多经典30／生存78，字段／顺序／边界／四位证据有界。核验重用原隔离命令执行，不能以核验时调用评分就当成新经历；capture的存在不等于允许发奖。

正式双模式自动保存、手动续玩／本局备份、载入及配套恢复已携带context，不在换模式、刷新或解包时丢弃。经典缓存增加growth对象身份：仅确认游标变化也重写核心检查点；未确认终局日志保留检查点，不在原完成统计成功后提前删掉。无growth的旧局维持原删除行为。

捕获属于旁路，不允许它推翻已完成的正式结算。内部成长上下文／证据发生异常时，两模式保留真实游戏结果，暂停本局后续成长捕获并在原保存提示区说明；已入账档案不撤销。当前开发预览导出降级为普通对局数据，不伪装成完整成长日志，后续读取按无growth旧局边界处理。原始内存中保留先前日志供定位，但不保证未入账的暂停日志可从降级导出恢复；不是自动清理玩家档案或修改游戏规则。

## 四、确认与去重

persistGrowthContext是协调写入下的批量后台接口，支持在同一档案候选中加入原终局统计；保存失败不返回已确认游标，重试不重复新增。读取、导入、恢复不会自动调用此接口。

- 已确认前缀必须存在于当前档案且values一致。主动恢复更早档案后凭据缺失时明确拒绝重补，保留对局，而不是利用checkpoint重放奖励。
- 同模式、root、完整authorityHash、阶段和位置的单元只登记一次，即使另一检查点的局部parent指针不同；复用原凭据与首次来源，不新建一份副本。原receipt key算法与旧记录不迁移；读取增加完整单元重复检查。
- 完整备份中的acknowledged前缀必须与配套profile匹配，序列化、解析及配套恢复都核对；standalone检查点可以只读核验，但后续保存确认游标必须有本机匹配档案。
- 两模式自动保存确认上下文前核验本机凭据，防止其他页明确替换档案后仍落盘一个已经失效的确认游标。

这里的摘要和checksum用于事实一致性，不是安全签名或联网领取证明。成就解析没有新增用户文件直接领取通道。
