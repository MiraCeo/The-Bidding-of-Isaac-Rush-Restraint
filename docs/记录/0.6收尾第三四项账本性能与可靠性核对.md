新增显式入口（在 `web` 执行）：

```powershell
npm run report:ledger:corpus -- --schema8
npm run report:ledger:capacity -- --schema8
npm run report:profile:performance -- baseline --schema8
npm run report:profile:performance -- repeat --schema8
npm run report:profile:performance -- optimized --schema8
```

- 无参数继续保留schema6默认行为；新增回归确认其编码未变化。schema8路径保留现行19字段房间证据、5字段层末证据及阶段启用头，不只改版本号。
- 五条模板由现行正式规则的Node生命周期生成，覆盖经典、最高难度观望／常规策略、简单难度常规／固定300策略。扩容时的身份／分支关系是人工规模夹具，不是玩家真实进度或可导入权威证明。

## 二、现行容量与一般保存

三种构成：classic、survival、mixed-branches；各测0／64／256／2048／4096／8192／12288／16384条，均附200条历史、32KiB扩展及128个完成凭据键。24个点中19点可读，5点被原预算拒绝。

| 构成 | 8192条整档／模块字节 | 12288条 | 16384条 |
| --- | --- | --- | --- |
| classic | 711082／621001 | 模块超限，拒绝 | 拒绝 |
| survival | 707217／617136 | 模块超限，拒绝 | 拒绝 |
| mixed-branches | 697961／607880 | 可读，但整批追加已超限 | 拒绝 |

混合12288点模块916997字节，低于896KiB上限；追加模板完整批次后变成919328字节，正确拒绝，原档案不变。**可读取、可追加一条、可追加一整批不是同一容量结论；16384是编码条数上限，不是任意内容都能保存16384条的保证。**

第一次schema8容量运行在这个点失败，因为旧测量脚本错误假定“可读就一定能整批追加”；失败目录和日志保留。修正测量器后独立计算候选编码字节，只在预测超预算时接受容量拒绝，其他异常仍报错，没有放宽生产校验或预算。

| 8192条构成 | 读取中位ms | 投影中位ms | 一般首存ms | 同档重复保存ms |
| --- | --- | --- | --- | --- |
| classic | 666.8 | 672.2 | 1505.5 | 727.4 |
| survival | 675.0 | 652.7 | 1529.8 | 729.2 |
| mixed-branches | 724.1 | 689.3 | 1574.1 | 730.2 |

- 重复保存不重复写玩家档案，但仍需核验现有正文，不能声称其成本已经为零。投影与保存主要成本仍随账本扫描增长；压缩往返在这些8192点约70–100ms量级，不是主要瓶颈。
- 精确1MiB整档可读取，增加1字节被拒绝；满档追加保留原档案，两个未确认成长单元继续待重试。
- 注入存储配额失败后没有档案写入或成长确认；解除失败后只写一次、确认两单元，重复重试字节不变。
- 2048成长＋8192完成凭据＋200历史＋32KiB扩展组合为899403字节，本夹具可读；不是所有事实组合都能同时达到各自条数上限。
- 这些是Node内存适配器／注入协调下的时间与边界，不是浏览器帧率、物理配额或所有用户档案的保证。

## 三、确认并修复的重复工作

经典 `serializeGameBackup` 内部对同一档案重复执行读取／配对校验。只为该**纯同步导出**套用已有 `withAchievementVerificationScope`：保留所有原校验与顺序，仅复用完整账本正文相同的私有扫描结果。作用域在函数返回前结束，不跨下载、storage回调、事件通知或异步边界，不引入长期缓存。

确定性回归：无成长配对的64条夹具扫描128→64次；带成长配对的65条夹具同样只扫描一次完整正文。两种情况导出字节与未复用参考严格相同；跨调用仍重新核验，损坏正文／非有限数拒绝，失败不污染后续导出。

同环境串行运行：Node24.15.0／V8 13.6.233.17-node.48／win32 x64、单worker，无并行构建或测试。三种构成各2048／8192，导出／解析／恢复及两模式完整备份分别3个样本取中位数，时间固定、性能时钟真实。先基线、同代码重复，再优化。

| 经典完整备份所附档案构成 | 条数 | 基线／重复／优化 导出中位ms |
| --- | --- | --- |
| classic | 2048 | 356.9／403.5／198.5 |
| classic | 8192 | 1491.3／1387.9／933.7 |
| survival | 2048 | 339.2／356.5／206.2 |
| survival | 8192 | 1473.1／1338.8／823.9 |
| mixed-branches | 2048 | 392.1／328.4／219.8 |
| mixed-branches | 8192 | 1421.7／1348.2／1539.3 |

**不隐去最后一个不利点。**优化运行后半段，未修改的独立档案和生存备份对照操作也从约0.7秒漂移到约1.5–1.7秒，因此跨运行耗时不能证明所有点普遍提速。优化成立的确定性门禁是扫描次数减少、全部校验保留与字节等价；计时只作本机参考，不承诺统一百分比，不把整体报告运行时间当用户操作耗时。

6个点的档案、成就投影、独立备份、经典完整备份、生存完整备份 **共30组SHA-256在基线／重复／优化间全部相同**。规模备份测量使用独立新检查点、不伪造其与人工账本的成长关联；真实成长配对另由下面的新档长流程验证。

## 四、现行新档可靠性

新增两条正式生产API长流程：

1. 经典以撒seed42，15房逐次真实结算／保存、逐房重载；第7房压缩备份往返并恢复到新的内存存储，再继续至终局。最终31条成长凭据、1次完成登记；重复保存、备份解析与只读回放解析3轮，不改变档案字节或达成时间。
2. 生存以撒seed3／简单／固定最高300正常报价，逐阶段保存／重载，第二层末完整备份恢复后继续。真人第五层淘汰，AI正常完成整局；真人成长不包含第25房之后的房间事实，完成只记一次。终局备份、回放解析、重复保存3轮保持原档案。

同时运行现有协调、取消、并发来源变化、失败回滚、缺协调能力、配对导入、只读查看、通知去重、本金／难度校验与容量边界等定向回归。**18文件220项通过**；另有语料、容量及三轮独立性能报告各1项通过。`tsc --noEmit`、`lint:client`通过。交互测试日志仍有React act诊断提示，不将其冒称零警告；本批无失败断言。

本轮后半段内置浏览器不可用，未修改其设置或换用旁路控制。可靠性新增证据是Node／happy-dom及生产API，不冒称本轮做了原生文件下载再导入、真实多页或物理配额测试。这些属于第5项独立门禁。前两项开发热更新现场的来源失效提示不作为稳定包故障结论；本批来源保护回归通过，不关闭缺原始样本的旧“成长上下文不一致”观察，也不扩大未分发试验档兼容。
