# 0.6.0独立档案核验复用与性能对照

日期：2026-10-16。用户授权先做可能的性能优化，按已定[0.6优化过渡版](../规划/0.6界面与性能优化过渡版.md)开始首批。**本轮只优化独立档案文件的同步处理，不改界面、不加功能、不改规则或存档协议。**应用推进0.6.0，不把优化继续记在0.5.12。

## 一、依据与最小改动

[0.5末期基线](./0.5末期账本容量与核验基线.md)中8192条Node备份往返约9秒。核对源码发现`player-profile-file.ts`的`validatedProfile`依次进行原始档案读取、受保护JSON往返后的读取、固定基线候选后的读取，当前未变化账本也进行了三次完整语义扫描。

本批保留上述所有校验语句和先后顺序，仅在**一次`validatedProfile`同步调用内**使用已有`withAchievementVerificationScope`：以完整、严格JSON形状的账本正文作为缓存键，最多4份私有核验快照；相同正文复用扫描，变化内容必须重新核验。返回仍为独立深拷贝；作用域在storage回调、事件通知、异步读取或后续操作之前结束，不扩大为全局长期缓存。

- 原始非有限数值、模块／整档预算、受保护JSON危险键、版本、基线、原因及父分支检查全保留。
- 未标记旧成果仍先验证再清理；派生权限与手动授权按原固定基线规则处理，新基线1不变。
- 不改`readPlayerProfile`公共验证器、账本扫描器、codec、同源锁、回滚或任何保存语义。本次不顺便删“看似重复”的防线。
- 范围为独立档案导出／解析／单键恢复；配套两模式备份、一般成长保存及UI投影不在本次优化声明内。

## 二、性能对照方法

新增独立入口：在`web`执行`npm run report:profile:performance -- baseline`或`-- optimized`。复用排他运行目录机制，每次分配新的`web/work/v05-closeout-ledger/capacity-随机串/`，结果类型为`profile-file-operation-performance`；目录前缀是通用报告分配器，不代表0.5被重新测量或覆盖。各点JSON、总报告及status均只创建一次。

经典／生存／混合分支三类，2048／8192两档，均有200条历史、32KiB扩展和128完成键。每个导出、解析、内存单键恢复测3次，取中位数；Date与build标签固定，计时用真实performance时钟，断言排除在操作计时之外。每点保留档案、备份与成就投影SHA-256，前后必须精确一致。

优化前在测量入口提交`236e9b6e85fc376befe1b230c340b81038496c0b`＋clean运行到`capacity-KWF321`，1项通过／189.06秒；运行代码仍为0.5.12的原验证序列。优化后在`fa93dc28772719ca0422bc8b2db7f8beebed8df4`＋clean运行到`capacity-WfrcvY`，1项通过／80.84秒。两次均Node24.15.0／V8 13.6.233.17-node.48／win32 x64、单worker，测量时未并行启动本批全量测试或构建；不把历史9秒与本次不同方法直接计算提速。

- **6个点的档案正文、导出备份及成就投影SHA-256分别前后完全相同。**数值变化来自扫描复用，不是少保存事实、改时间、删凭据、跳过危险键检查或把旧成果补发。

- 同步核验后仍有约1.5～1.6秒的8192条单操作成本；后续继续依据测量分析，不在本批顺便引入Worker、长期缓存、异步领取或新格式。
- 原始报告、分点样本、status、源码与环境在各自独立目录；对照表和哈希核对另存`web/work/v060-profile-performance/comparison.json`。旧报告不覆盖。
