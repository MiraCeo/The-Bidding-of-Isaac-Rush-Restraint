## 三、最小技术增量与兼容

### 权威事实

`room-engine.ts`仅旁路观察本次已经确定的合作落选与高价第N＋1；先排除同组全部资格，再排除实际发放。证据通过`room-near-miss-evidence.ts`的WeakMap绑定原scoreBreakdowns对象，不增加可枚举结算字段，不改变随机调用次数、名额、分配、计分或AI；JSON复制不能制造证据。正式控制器捕获时提取为成长原因事实，缺证据时保留待核验，不按最终零道具倒推原因。

新增`complete`终局阶段：模式、五角色编号、是否真实冠军。经典与生存各自完成流程生成，浏览／只读回放不生成。E08仅由已保存凭据推导可选5位角色位集，不维护另一套总账。

### 成长上下文与账本

- v5对局、growth1、档案正文1、独立档案文件1及压缩容器1不改。growth1增加可选`expansionFrom`阶段边界；缺失表示旧上下文，恢复核验仅重建旧事实，新现场观察才设边界。不使用日期或应用版本号猜测已领奖。
- 新room事实在旧5个值后增加第6个原因位（0～3）；旧5值表示“旧版本没有观察此原因”，不等于新观察后两项均为false。
- 固定模块名`achievementRegistryV1`新增内部schema3／catalogVersion2；含扩展事实即使用schema3，即使不足256条。旧schema1／catalogVersion1及schema2／catalogVersion1继续严格读取；无扩展事实仍按既有256条阈值写schema2；已有schema3不降级。
- schema3沿用schema2的完整root／parent／authority／key／时间编码；每条room旧值后增加一项varint，0表示旧5值，1～4表示新原因码＋1；stage4为complete，保留旧stage0～3。全部旧节点key与时间不重建、不丢失。逻辑读取视图不是传输格式，必须经正式安装／编码函数写回，不能将归一化视图直接当旧schema1文件序列化。
- 同一权威单元旧5值与新6值比较旧事实一致时只去重，保留旧凭据，不用新原因补奖；两个已带新原因的事实互相矛盾时拒绝。确认前缀与配套恢复采用同一兼容比较，不补已回退移除的凭据。
- 新经典完整日志最多31单元、终局序位34；理论完整生存最多79单元、终局序位78。导入忽略前缀、档案代次、同源锁、CAS原文守卫、失败回滚及pending重试继续覆盖所有新单元。
- 896KiB模块、1MiB整档、16384条紧凑凭据等预算保持，不声称无限容量。旧容量报告继续使用冻结旧语料，不把它当新增schema3最坏容量的实测结果。
- **早期0.5程序不支持schema3或扩展growth时明确拒绝，不能当空档重奖。**携带新模块的独立档案和配套备份需使用0.5.3及后续兼容读取器；旧HTML不改写。
